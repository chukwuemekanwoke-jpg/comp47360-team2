## Context

Tablé is a Manhattan-focused dining marketplace prototype: geospatial discovery, ETA-guarded in-app booking, and 1-to-1 flash deals on **simulated/historical** restaurant data (not production OpenTable or live reservation APIs).

The team has six members. Architecture must stay deliverable within the practicum timeline while satisfying course requirements (web + mobile, ML, EDI, ≥2 datasets).

This ADR records **what we build now** versus **what we may add later**. Earlier revision 2 described a multi-language microservice platform that does not match the current codebase; revision 3 corrected that; revision 4 aligned web stack, auth, ETA API, and real-time strategy with the codebase; revision 6 reconciles the document with what actually shipped (push notifications, Terraform), corrects the data-source description in ADR-001-E, and records the infrastructure decommission.

> **Infrastructure status (2026-08-01):** both `tabl-app-staging` and `tabl-app-prod` GCP projects were deleted and the billing account closed. The Cloud Run / Cloud SQL decisions below describe the architecture as deployed and measured up to that date; nothing in this ADR currently points at a live environment. See [`cloud_deployments/README.md`](../../cloud_deployments/README.md) for how to run the services locally instead.

## ADR-001-A: Backend language and runtime

**Status:** Accepted (MVP)

### Decision

- **API gateway and business logic:** Node.js **20+** with **Express 5** (JavaScript), single deployable under `backend/api-gateway/`.
- **ML inference only:** Python **FastAPI** under `ml-pipeline/fastapi-app/`.
- **No Spring Boot, NestJS, or additional backend languages** for the practicum MVP.

### Rationale

- Matches implemented BE-1 (`/health`) and BE-3 routes under `/api/v1`.
- One process simplifies integration for a six-person team.
- Business plan and root README already specify Node.js + Express.

### Consequences

- All P0 HTTP endpoints live in the gateway until post-MVP split is justified.
- OpenAPI / contract: [docs/openapi-v0.yaml](../openapi-v0.yaml) and [docs/api-contract-v0.md](../api-contract-v0.md).

## ADR-001-B: Service decomposition (logical modules, monolith deployment)

**Status:** Accepted (MVP) · **Proposed (future):** separate deployables

### Decision (MVP)

One Express application with **route modules** mapped to domains:

| Module | Responsibility | P0 stories |
|--------|----------------|------------|
| Users | Onboarding, preferences | 1.1 |
| Restaurants | Nearby discovery, detail | 2.1 |
| Bookings | ETA validation, holds, confirm | 3.1, 3.2 |
| Offers | Inbox, accept, TTL 900s | 4.1 |
| Campaigns | B-side lull mitigation, auto-complete | 5.2 |

### Explicitly not in MVP

- Independent `reservations-service`, `marketplace-service`, `notifications-service`, or `user-profile-service` deployments.
- Seven-container production mesh described in early drafts.
- Separate `backend/realtime/` service.

### Consequences

- PostgreSQL is the system of record; no distributed transactions across services in MVP.
- Campaign completion and offer revocation use DB triggers (see BE-2 migration).

## ADR-001-C: ML pipeline

**Status:** Accepted

### Decision

- **FastAPI** service for: busyness signals, user–deal matching, recommendation scores.
- **Stateless:** no auth, no booking workflow ownership; gateway persists results to PostgreSQL.
- Contract preview: `POST /api/v1/match` (see API contract §5).

### Constraints

- ML does not call OpenTable production APIs.
- Training data (**corrected in revision 6** — see ADR-001-E): **Google Places popular-times index** as the supervised label, **NYC TLC** taxi drop-off aggregates, and **NYC PLUTO** land-use data. No OpenTable dataset is used.

### Consequences

- Gateway inserts `offers` after match (`expiresAt = now + 900s`).
- Production may start with heuristic/random match; trained models replace heuristics when ready.

## ADR-001-E: Restaurant data and reservations (MVP)

**Status:** Accepted

### Decision

**In scope for MVP**

- Restaurant and availability data stored in **our PostgreSQL** (seed + simulated updates).
- **In-app booking** with `available_table_count`, **15-minute** hold window, platform-managed `bookings` / `campaigns` / `offers` (BE-2 schema).

**Busyness modelling data (rewritten in revision 6).** Revisions 1–5 described the
training data as "OpenTable-style historical feeds" and listed Google Places as
out of scope. That is not what was built, and the description is corrected here:

| Source | Role in the model |
| --- | --- |
| **Google Places** popular-times index | The supervised **label** — a published 0–100 hourly activity value, used as a proxy for occupancy |
| **Google Places** venue attributes | Core features: rating, review count, typical visit duration |
| **NYC TLC** yellow-taxi records | Area-activity feature, aggregated per (taxi zone, weekday, hour) |
| **NYC PLUTO** land-use data | Floor-area estimation, feeding capacity and turnover |

**No OpenTable dataset is used anywhere in `ml-pipeline/`.** Google Places is
therefore *in* scope as a feature and label source, while remaining *out* of
scope as a live discovery API — the two are separate decisions and earlier
revisions conflated them.

**Out of scope for MVP**

- OpenTable Partner API, OpenTable datasets, or live slot locking.
- **Google Places API called at request time** as a discovery source; venue attributes are ingested offline into `restaurant_features.parquet`, never fetched live.
- Deep links to external resy/OpenTable as the main booking path.

### Consequences

- The label is a **published activity proxy, not observed occupancy**; model figures measure fidelity to that index, not queue-time accuracy.
- [`docs/data-strategy.md`](../data-strategy.md) still carries the superseded OpenTable framing (7 references) and needs the same correction — tracked, not yet applied.
- B-side dashboard uses same API as C-side (`POST .../campaigns`).

## ADR-001-F: Reachability guardrail (ETA)

**Status:** Accepted

### Decision

- **Backend is authoritative** for `canBook` (frontend display is advisory).
- **Primary:** Google **Routes API** (`computeRouteMatrix`) — one call when opening restaurant detail or confirming a booking; cache ~5 minutes (cost control).
- **Fallback:** local haversine + fixed-speed estimate when no API key, timeout, or API error.
- **Note:** Google Distance Matrix API is deprecated; Tablé uses Routes API instead.

### Product constants

- Hold window: **15 minutes** (`restaurants.hold_window_minutes`).
- Discovery radius: **1500 m**.

### Consequences

- Implemented via `GET /api/v1/restaurants/:id/eta` (BE-12).
- Env: `GOOGLE_MAPS_API_KEY` in gateway `.env.example` (enable **Routes API** on the GCP project).

## ADR-001-G: Real-time and notifications

**Status:** Accepted (MVP) for REST polling · **Accepted (rev 6)** for push notifications · **Proposed (Phase 2)** for WebSockets

### Decision (MVP)

- Flash deals delivered via **REST inbox** (`GET /users/me/offers`); clients **poll** or refetch on navigation; countdown from `secondsRemaining` / `expiresAt`.
- Map busyness and availability refresh via **REST** (`GET /restaurants/nearby`) on location change or manual pull-to-refresh.
- **No** mandatory Socket.IO, Redis Pub/Sub, or WebSocket service for MVP.

### Push notifications (shipped — status changed in revision 6)

Revisions 1–5 filed push notifications under *Proposed (post-MVP)*. They were
delivered in Sprint 4 and are now part of the MVP:

- Implemented **client-side in the mobile app** (`frontend/mobile-app/src/services/pushNotifications.ts`) using Expo notifications with Firebase Cloud Messaging as the transport.
- **The gateway holds no FCM integration** — no Firebase SDK, credentials or send-path exists in `backend/api-gateway/`. This is a deliberate consequence of the decision above: the gateway stays a pure REST service and the client owns token registration and delivery.
- The REST offer inbox remains the source of truth; a push is a prompt to refetch, never the payload itself.

### Still proposed (post-MVP)

- WebSockets for occupancy push if polling proves insufficient.
- Anti-fatigue rules (e.g. max 3 deals / 7 days) — not implemented.

### Consequences

- Frontend strategy and mobile/web clients use REST + RTK Query cache invalidation, not a realtime service.
- Because delivery is client-side, an offer's authoritative expiry is always `expiresAt` from the API, not the notification's own timing.

**Status:** Withdrawn (2026-07-21)

## ADR-001-I: Frontend and mobile

**Status:** Accepted

### Decision

| Client | Stack | Path |
|--------|-------|------|
| Web | React, **Vite**, Tailwind | `frontend/web-app/` |
| Mobile | **React Native**, **Expo**, NativeWind | `frontend/mobile-app/` |
| Shared API client | Redux Toolkit Query | `frontend/packages/shared/` |

### MVP integration

- Consume `http://localhost:3001` (gateway) per [api-contract-v0.md](../api-contract-v0.md).
- **Authentication:** JWT via `Authorization: Bearer <token>` from `POST /api/v1/auth/login` and `POST /api/v1/auth/register`. Interim `X-User-Id` header remains supported for dev/demo until all clients migrate.
- JSON **camelCase**; shared types in `frontend/packages/shared/src/types.ts`.

### Deferred

- Shared `packages/ui` monorepo package — add only if duplication hurts velocity.
- Mobile biometric login — platform-specific, optional later.

### EDI

- Accessible UI, manual neighbourhood fallback (P1), and restaurant EDI flags in schema (`is_wheelchair_accessible`, `sensory_friendly`). Declared diner accessibility needs are backend-enforced eligibility constraints for campaign matching, including the distance fallback used when ML is unavailable.

## ADR-001-K: Rate limiting

**Status:** Accepted (recorded in revision 6; implemented Sprint 4)

### Decision

IP-based rate limiting on the gateway, not per-user or per-token:

| Limiter | Scope | Budget |
|---------|-------|--------|
| `authRateLimiter` | all `/auth/*` routes | 20 requests / 15 min / IP (`RATE_LIMIT_AUTH_MAX`) |
| `writeRateLimiter` | `POST /bookings`, `POST /campaigns` | 60 requests / 15 min / IP (`RATE_LIMIT_WRITE_MAX`) |

Read endpoints (`nearby`, `eta`, `revpash`, restaurant detail) are not limited.

### Rationale

Cheap protection for a public demo against credential stuffing and booking
spam, with no session store required.

### Consequences

- **Load testing is constrained by this decision.** A single-origin k6 run is one IP, so booking-creation throughput cannot be measured representatively without raising `RATE_LIMIT_WRITE_MAX` for the test window. This is why booking creation is absent from the paper's service-performance results — a measurement gap caused by an architectural choice, not an oversight.
- Any future load test must log in once per virtual user and reuse the JWT, or it will hit 429s at VU 21 regardless of system capacity.

## Superseded decisions (revision 2 — do not follow)

The following are **withdrawn** unless explicitly revived in a future ADR:

- Spring Boot / NestJS polyglot backend
- Seven independently deployed microservices as MVP
- Google Places as primary restaurant source; removal of OpenTable **datasets** from scope
- Mandatory Redis + Socket.IO for MVP KPI
- Next.js for web frontend (superseded by React + Vite)
- Google Distance Matrix API for ETA (superseded by Routes API)
- Repository layout `apps/`, `services/`, `packages/`, `infra/terraform` as current structure
- External-only reservation workflow (deep links) replacing in-app `bookings`
- `docs/ER_Diagram.md` normalized ER model (superseded by `database/schema.md`)
- Generative AI / Dining Copilot (ADR-001-H); no OpenAI integration planned

### Superseded in revision 6

- **"OpenTable-style historical datasets" as the ML training source** — no OpenTable data exists in `ml-pipeline/`; the label is the Google Places popular-times index (ADR-001-E).
- **Google Places as wholly out of scope** — out of scope as a live discovery API, in scope as an offline feature and label source (ADR-001-E).
- **Push notifications as post-MVP** — shipped Sprint 4, client-side (ADR-001-G).
- **Terraform as deferred** — built under `cloud_deployments/` (ADR-001-J).
