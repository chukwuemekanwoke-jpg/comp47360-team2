## Context

Tablé is a Manhattan-focused dining marketplace prototype: geospatial discovery, ETA-guarded in-app booking, and 1-to-1 flash deals on **simulated/historical** restaurant data (not production OpenTable or live reservation APIs).

The team has six members. Architecture must stay deliverable within practicum sprints while satisfying course requirements (web + mobile, ML, GenAI, EDI, ≥2 datasets).

This ADR records **what we build now** versus **what we may add later**. Earlier revision 2 described a multi-language microservice platform that does not match the current codebase; revision 3 corrects that.

## ADR-001-A: Backend language and runtime

**Status:** Accepted (MVP)

### Decision

- **API gateway and business logic:** Node.js **20+** with **Express 5** (JavaScript), single deployable under `backend/api-gateway/`.
- **ML inference only:** Python **FastAPI** under `ml-pipeline/fastapi-app/` (Sprint 3+).
- **No Spring Boot, NestJS, or additional backend languages** for the practicum MVP.

### Rationale

- Matches implemented BE-1 (`/health`) and planned BE-3 routes under `/api/v1`.
- One process simplifies integration for a six-person team.
- Business plan and root README already specify Node.js + Express.

### Consequences

- All P0 HTTP endpoints live in the gateway until post-MVP split is justified.
- OpenAPI / contract: [docs/openapi-v0.yaml](../openapi-v0.yaml) and [docs/api-contract-v0.md](../api-contract-v0.md).

## ADR-001-B: Service decomposition (logical modules, monolith deployment)

**Status:** Accepted (MVP) · **Proposed (future):** separate deployables

### Decision (MVP)

One Express application with **route modules** mapped to domains:

| Module | Responsibility | P0 stories |
|--------|----------------|------------|
| Users | Onboarding, preferences | 1.1 |
| Restaurants | Nearby discovery, detail | 2.1 |
| Bookings | ETA validation, holds, confirm | 3.1, 3.2 |
| Offers | Inbox, accept, TTL 900s | 4.1 |
| Campaigns | B-side lull mitigation, auto-complete | 5.2 |

Optional later folders (not separate repos in MVP): `realtime/` only if WebSocket polling is insufficient.

### Explicitly not in MVP

- Independent `reservations-service`, `marketplace-service`, `notifications-service`, or `user-profile-service` deployments.
- Seven-container production mesh described in early drafts.

### Consequences

- PostgreSQL is the system of record; no distributed transactions across services in MVP.
- Campaign completion and offer revocation use DB triggers (see BE-2 migration).

## ADR-001-C: ML pipeline

**Status:** Accepted

### Decision

- **FastAPI** service for: busyness signals, user–deal matching, recommendation scores.
- **Stateless:** no auth, no booking workflow ownership; gateway persists results to PostgreSQL.
- Contract preview: `POST /api/v1/match` (see API contract §5).

### Constraints

- ML does not call OpenTable production APIs.
- Training data: **OpenTable-style historical datasets** and **NYC Open Data** (and related open sources per business plan).

### Consequences

- Gateway inserts `offers` after match (`expiresAt = now + 900s`).
- Sprint 3 integrates inference; Sprint 2 may use heuristic/random match until model is ready.

## ADR-001-D: Data layer and local development

**Status:** Accepted

### Decision

| Layer | Technology | MVP |
|-------|------------|-----|
| Primary database | PostgreSQL 16 | Yes — `database/migrations/` |
| Local Postgres | Docker Compose | Yes — `database/docker-compose.yml` |
| Cache (Redis) | Memorystore / local Redis | **Deferred** (Phase 2) |
| Time-series warehouse | BigQuery / TimescaleDB | **Deferred** (analytics / paper only if needed) |

- Geo: `latitude` / `longitude` on `restaurants`; haversine in API/SQL (**1500 m** discovery radius).
- Optional PostGIS: `database/migrations/002_postgis_optional.sql` (manual, not default).

### Consequences

- Team standard: `cd database && npm run db:up && npm run migrate`.
- `DATABASE_URL` shared with api-gateway via `.env` (never committed).

## ADR-001-E: Restaurant data and reservations (MVP)

**Status:** Accepted

### Decision

**In scope for MVP**

- Restaurant and availability data stored in **our PostgreSQL** (seed + simulated updates).
- Historical / structured **OpenTable-style** feeds and **NYC Open Data** for busyness modelling (per business plan risk mitigation: *simulate live updates from batches*).
- **In-app booking** with `available_table_count`, **15-minute** hold window, platform-managed `bookings` / `campaigns` / `offers` (BE-2 schema).

**Out of scope for MVP**

- OpenTable Partner API, OAuth, or live slot locking.
- **Google Places API** as primary discovery source (optional future enrichment only).
- Deep links to external resy/OpenTable as the main booking path.

### Consequences

- Action items: BE-9 seed data; Data & ML cleaning pipeline; no “remove OpenTable backlog” — instead **use open/historical OpenTable datasets offline**.
- B-side dashboard uses same API as C-side (`POST .../campaigns`).

## ADR-001-F: Reachability guardrail (ETA)

**Status:** Accepted

### Decision

- **Backend is authoritative** for `canBook` (frontend display is advisory).
- **Primary (user stories):** Google **Distance Matrix** — one call when opening restaurant detail; cache ~5 minutes (cost control).
- **Fallback (course-friendly):** OSRM / open routing if API quota or budget blocks Google.

### Product constants

- Hold window: **15 minutes** (`restaurants.hold_window_minutes`).
- Discovery radius: **1500 m**.

### Consequences

- Implemented via `GET /api/v1/restaurants/:id/eta` (BE-3).
- Env: `GOOGLE_MAPS_API_KEY` in gateway `.env.example` (optional until Sprint 2).

## ADR-001-G: Real-time and notifications

**Status:** Proposed (Phase 2) for WebSockets · **Accepted (MVP)** for inbox polling

### Decision (MVP)

- Flash deals delivered via **REST inbox** (`GET /users/me/offers`); client countdown from `secondsRemaining` / `expiresAt`.
- **No** mandatory Socket.IO, Redis Pub/Sub, or `backend/realtime/` service for Sprint 2–3 demo.

### Proposed (post-MVP)

- WebSockets for occupancy push if polling is insufficient.
- Push notifications (e.g. Firebase) and stricter anti-fatigue rules (e.g. max 3 deals / 7 days) after core loop works.

### Consequences

- README may mention `realtime/` as a **placeholder**; do not block MVP on it.

## ADR-001-H: Generative AI (Dining Copilot)

**Status:** Proposed (Sprint 4 per business plan)

### Decision

- **OpenAI** (or equivalent) for conversational “Dining Copilot” and explanation UX — **not** replacing FastAPI scoring for match/busyness.
- Sprint 4 integration; transparent UX; follow course budget for API tokens.

### Consequences

- ML Lead owns model metrics; Backend exposes optional chat proxy route in Sprint 4+.
- Does not change BE-2 tables in Sprint 1–3.

## ADR-001-I: Frontend and mobile

**Status:** Accepted

### Decision

| Client | Stack | Path |
|--------|-------|------|
| Web | React, **Next.js** | `frontend/web-app/` |
| Mobile | **React Native**, **Expo** | `frontend/mobile-app/` |

### MVP integration

- Consume `http://localhost:3001` (gateway) per [api-contract-v0.md](../api-contract-v0.md).
- Auth stub: header `X-User-Id` after dummy onboarding.
- JSON **camelCase**; map prototype mocks to API fields (contract §7).

### Deferred

- Shared `packages/ui`, `packages/api-client` monorepo packages — add only if duplication hurts velocity.

### EDI

- Accessible UI, manual neighbourhood fallback (P1), restaurant EDI flags in schema (`is_wheelchair_accessible`, `sensory_friendly`).

## Superseded decisions (revision 2 — do not follow)

The following are **withdrawn** unless explicitly revived in a future ADR:

- Spring Boot / NestJS polyglot backend
- Seven independently deployed microservices as MVP
- Google Places as primary restaurant source; removal of OpenTable **datasets** from scope
- Mandatory Redis + Socket.IO for MVP KPI
- Repository layout `apps/`, `services/`, `packages/`, `infra/terraform` as current structure
- External-only reservation workflow (deep links) replacing in-app `bookings`
